# Declarative Contract Architecture (DCA)

> Любая часть системы самодостаточна — но спроектирована так, что естественно стыкуется с остальным.

---

## Манифест

DCA — это не список правил. Это один принцип повторённый на всех уровнях: каждая часть системы знает своё место, выражает его через контракт, и не мешает остальному. Из этого вытекает всё остальное.

**Нет исключений — есть переходы:**

- Ошибка — не исключение. Это переход между состояниями.
- Граница — не стена. Это точка входа с контрактом.
- Тест — не отдельная работа. Это маршрут который уже описан в flow.
- Лог — не пожарный инструмент. Это часть контракта модуля.
- Версия — не бюрократия. Это уважение к тем кто зависит от тебя.
- Декларация — не документация. Это система которая объясняет себя сама.

**Формула:**

```
Система = Модули + Контракты + События + Декларация + Flow
```

Хорошая архитектура — это когда систему можно пересобрать как LEGO: любой модуль можно заменить, не сломав остальное, потому что все связи выражены через контракты.

> Хорошая система не требует героизма. Она спроектирована так, что правильное поведение — это путь наименьшего сопротивления.

---

## Группа I — Что такое система

### 01. Модуль

Модуль — это единица системы. Не файл, не папка, не класс — а смысловая единица с тремя свойствами:

- **Контракт** — что модуль принимает и что отдаёт. Ожидание поведения.
- **Зона ответственности** — одна причина для изменения. Если модуль меняется по двум причинам — это два модуля.
- **Изоляция** — модуль не знает про детали реализации соседей. Только контракты.

Размер не имеет значения. Функция, React-компонент, NestJS-модуль, микросервис — всё это модули. Разница только в масштабе, но не в принципах.

**Принципы одинаковы на всех уровнях — меняется только масштаб. Это главное.**

**Антипаттерн:** UserService знает про Order, вызывает напрямую внутренности OrderService. Граница нарушена.

**Правило:** UserService работает только с интерфейсом OrderPort. Что внутри OrderService — не его дело.

**Связь с другими концепциями:**
- DDD определяет что является модулем (домен)
- Hexagonal защищает границы модуля (порты)
- Event-driven связывает модули без прямых зависимостей

---

### 02. Контракт

Контракт — это описание ожидаемого поведения модуля. Не реализация — только ожидания.

Формы контракта: TypeScript-интерфейс, OpenAPI-схема, GraphQL-схема, тип, event payload. Конкретная форма не важна — важно что контракт **явный**.

> Контракт — основа слабой связанности. Модули знают только контракты друг друга, не реализации.

**Контракт включает поведение при ошибке.** Большинство контрактов описывают только успешный сценарий. Но полный контракт декларирует оба пути:

```typescript
interface PaymentPort {
  // happy path
  pay(orderId: string, amount: number): Promise<PaymentResult>

  // error path — часть контракта, не сюрприз
  // throws: PaymentDeclinedError | NetworkError
}
```

**Откуда берутся контракты:** контракты не придумываются в вакууме. Они кристаллизуются из опыта:

```
Неизвестная ситуация → generic обработчик → наблюдение паттерна → явный контракт
```

**Версионирование контрактов** (связь с разделом 09): контракты меняются. Система эволюционирует, и контракты должны тоже. Задача — делать это без поломки зависимых модулей:
- Additive changes — добавление полей обратно совместимо
- Breaking changes — требуют версионирования (v1/v2) или deprecation-периода
- Event contracts — особенно хрупкие, нужна строгая типизация payload

---

### 03. Типы модулей

Нет "грязных" и "чистых" модулей. Есть разные типы с разными характеристиками.

#### Pure — вычисляет

Нет сайд-эффектов. Детерминированы: одни и те же входные данные — всегда один результат. Легко тестировать.

```typescript
function calculatePrice(cart: Cart): number {
  return cart.items.reduce((sum, item) => sum + item.price, 0)
}
// не знает про БД, стор, API — только считает
```

#### Stateful — хранит

Управляет состоянием. Предоставляет доступ через контракт. Может эмитить события при изменении.

**Store — не глобальная помойка, а узел синхронизации системы.**

```typescript
interface CartStore {
  getItems(): CartItem[]
  addItem(item: CartItem): void
  onChange(cb: Callback): Unsubscribe
  // бизнес-логика здесь НЕ живёт
}
```

#### Effectful — взаимодействует с миром

API, БД, файловая система. Недетерминированы, медленные, ненадёжные.

**Сайд-эффект — это просто модуль с внешней зависимостью. Не страшно, если изолировано.**

```typescript
class StripePaymentAdapter implements PaymentPort {
  async pay(orderId, amount) {
    return await stripe.charge({ orderId, amount })
  }
}
```

**Поток ответственности:**
```
Pure вычисляет → Stateful хранит → Effectful синхронизирует с миром
```

**Антипаттерны:** бизнес-логика в store, HTTP-запрос внутри компонента, состояние в pure функции через closure.

---

### 04. События

Обычный контракт описывает что вызвать. Событие описывает что произошло. Это принципиально разные модели связи.

```
// вызов (жёсткая связь)
orderService.create() → paymentService.pay() → emailService.send()

// событие (слабая связь)
emit("orderCreated") → подписчики реагируют независимо
```

**Событие — это контракт во времени.** Обычный контракт — пространственная связь. Событие — связь во времени.

```typescript
// отправитель не знает кто слушает
eventBus.emit('orderCreated', { orderId, userId, total })

// payment — просто подписчик
eventBus.on('orderCreated', async (order) => {
  await paymentService.pay(order)
  eventBus.emit('orderPaid', order)
})

// notification — независимый подписчик
eventBus.on('orderPaid', (order) => {
  emailService.send(order.userId, 'Заказ оплачен')
})
```

**Event Bus — модуль управления причинно-следственными связями.** Именно здесь живёт порядок событий, async, retry при падении обработчика.

**Что нужно раскрыть:**
- Типизация event payload — строгий контракт на содержимое события
- Idempotency — обработчик может получить событие дважды, должен быть к этому готов
- Порядок событий — как работать когда они приходят не в том порядке

## Группа II — Как система собрана и ведёт себя

### 05. Декларативный слой

Декларативный слой — это мета-уровень над системой модулей. Он описывает **как собрать систему из модулей**, не описывая что внутри модулей.

> Декларативность — это ООП, поднятый на уровень выше. ООП инкапсулирует поведение. Декларативность описывает композицию этих поведений извне.

**Пример — модалки через конфиг:**

```typescript
const modals = {
  'confirm-order': {
    component: ConfirmOrderModal,
    size: 'md',
    closeOnOverlay: true,
  },
  'payment-error': {
    component: PaymentErrorModal,
    size: 'sm',
    closeOnOverlay: false,
  }
}

modalService.open('confirm-order', { orderId })
// модалки перестали быть "глобальными зависимостями"
```

**Lookup table вместо if/else:**

```typescript
// антипаттерн
if (role === 'admin') { return adminDashboard }
else if (role === 'user') { return userDashboard }

// декларативно
const dashboardByRole = {
  admin: AdminDashboard,
  user:  UserDashboard,
  guest: GuestDashboard,
}
return dashboardByRole[role]
```

**Граница декларативности:**

✓ Можно декларировать: связи между модулями, конфигурацию компонентов, переходы между состояниями, маршруты и роли.

✗ Нельзя декларировать: бизнес-логику в JSON, условия в строках ("if": "x > 5"), алгоритмы. Это превращается в нечитаемый DSL.

---

### 06. Flow / State Machine

Декларативный слой описывает структуру системы. Но система живёт во времени — нужен слой который описывает **поведение во времени**.

> Если декларативность описывает структуру, то flow слой описывает поведение системы во времени.

**User Story → State Machine:** берём user story и насаживаем на конечный автомат:
```
user story → шаги → состояния → переходы → конфиг автомата
```

**Главная проблема без flow — неопределённое состояние.** Пользователь нажал "оформить заказ". Запрос ушёл на бэк. Заказ создан в БД. Соединение оборвалось. Пользователь нажимает ещё раз — дубль заказа.

State machine делает состояния явными — включая `unknown`:

```javascript
const checkoutFlow = {
  initial: 'idle',
  states: {
    idle:             { on: { SUBMIT: 'validating' } },
    validating:       { on: { VALID: 'submitting', INVALID: 'failed' } },
    submitting:       { on: { SUCCESS: 'processing', NETWORK_ERROR: 'retrying', TIMEOUT: 'unknown' } },
    processing:       { on: { CONFIRMED: 'done', REJECTED: 'failed' } },
    retrying:         { on: { SUCCESS: 'processing', EXHAUSTED: 'failed_permanent' } },
    unknown:          { on: { CHECK: 'submitting' } }, // ← потеряли связь — явное состояние
    done:             {},
    failed:           { on: { RETRY: 'validating' } },
    failed_permanent: {},
  }
}
// unknown — не ошибка. Это "мы не знаем что произошло, нужно проверить"
```

**Retry как декларативная политика, не магия:**

```javascript
// конфиг — ЧТО происходит
const paymentFlow = {
  states: {
    submitting: {
      on: {
        NETWORK_ERROR: 'retrying',  // unexpected → retry
        DECLINED:      'failed',    // expected → no retry
        INVALID:       'failed',    // domain violation → no retry
      }
    },
    retrying: {
      retry: { max: 3, backoff: 'exponential' },
      on: { SUCCESS: 'done', EXHAUSTED: 'failed_permanent' }
    },
  }
}

// код — КАК происходит
onEnter('retrying', async (ctx) => {
  await delay(ctx.attempt * 1000) // exponential backoff
  await orderService.submit(ctx.order)
})
```

> Retry, fallback, circuit breaker — это не отдельные паттерны. Это описание того как модуль ведёт себя при переходах между состояниями.

**Правило:** в конфиге — состояния и переходы. В коде — что делать при входе в состояние. Никогда не наоборот.

**Нотификации через flow** — уведомления реагируют на состояния, не на random события:

```javascript
checkoutFlow.onEnter('done', () => notify.success('Заказ оформлен'))
checkoutFlow.onEnter('failed_permanent', () => notify.error('Не удалось оформить заказ'))
checkoutFlow.onEnter('unknown', () => notify.warning('Проверяем статус заказа...'))
```

**State machine vs Event Bus:** не конкуренты. State machine управляет внутренним поведением модуля. Event bus — связью между модулями. Переход в состояние эмитит событие в шину.

## Группа III — Как система живёт и учится

### 07. Обработка ошибок

Философски — ошибка это **нарушение контракта**. Модуль обещал поведение и не выполнил.

Практически — нужно обращаться с ошибкой как с **абстрактным generic событием**, классифицировать его, и только после классификации превращать в явный контракт.

> Мудрость — это библиотека обработанных исключений. Generic обработчик — инкубатор будущих контрактов.

**Жизненный цикл ошибки:**
```
Неизвестная ошибка → catch(Error) + log → наблюдение паттерна → PaymentDeclinedError → явный обработчик
```

#### Три типа ошибок

**Expected (ожидаемые)** — платёж отклонён, пользователь не найден. Валидный исход, не баг. Должны быть в контракте модуля как явный путь. *Retry бессмысленен.*

**Unexpected (неожидаемые)** — упала БД, timeout, сеть. Система не знала что так бывает. Попадают в generic обработчик → наблюдение → eventual контракт. *Retry применим.*

**Domain violation (нарушение инварианта)** — заказ с пустой корзиной. Нарушение правил домена. *Retry опасен — повторишь нарушение.*

Большинство кодовых баз валят всё это в один catch. Это источник хаоса.

**Полный контракт декларирует все исходы:**

```typescript
interface PaymentPort {
  /**
   * @throws {PaymentDeclinedError}  — expected, карта отклонена
   * @throws {NetworkError}          — unexpected, нет связи → retry
   * @throws {InvalidAmountError}    — domain violation, сумма некорректна
   */
  pay(orderId: string, amount: number): Promise<PaymentResult>
}
```

#### Паттерны реакции — переходы между состояниями

**Retry** — только для Unexpected. Переход: `failed → retrying → processing | failed_permanent`

**Fallback** — альтернативное поведение при недоступности модуля. Переход: `failed → degraded (fallback mode)`

**Circuit Breaker** — перестать обращаться к упавшему модулю на время. Состояния: `closed → open → half-open → closed`

**Dead Letter Queue** — события которые не удалось обработать. Отдельный stateful модуль. Сохраняем, не теряем, разбираем отдельно:
```
failed_permanent → Dead Letter Queue → ручной разбор / алерт → retry или discard
```

> Ошибка без явного состояния — это стихийный пожар. Ошибка как переход в flow — это управляемая деградация.

### 08. Observability

Обычно логи — "добавлю потом когда сломается". В DCA — это **четвёртая часть контракта** модуля, декларируется с самого начала.

```typescript
interface PaymentModule {
  // 1. что принимает
  pay(orderId: string, amount: number): Promise<Result>

  // 2. что возвращает → Result

  // 3. что выбрасывает
  // throws: PaymentDeclinedError | NetworkError

  // 4. какие события эмитит (observability contract)
  // emit: payment.started | payment.succeeded | payment.failed
}
```

**Разные проблемы — разные инструменты:**
- Лог сообщение — чаще всего. Проблемы в бизнес-логике, в потоке данных.
- Состояние стора — реже. Race conditions, неожиданные мутации.
- Стек трейс — совсем редко. Технические падения, null/undefined.

> Если чаще всего помогает лог — значит большинство проблем логические, а не технические. Система работает, но делает не то.

#### Два подхода

**А — модуль логирует себя сам.** Просто написать, но модуль зависит от logger. Хочешь сменить Sentry на Datadog — идёшь в каждый модуль.

**Б — модуль эмитит события, logger подписан.** Модуль не знает про logger вообще:

```typescript
class PaymentModule {
  async pay(orderId, amount) {
    // логика
    eventBus.emit('payment.failed', { orderId, reason })
    // не знает кто слушает
  }
}

class LoggerModule {
  constructor() {
    eventBus.on('payment.failed', (e) => logger.error(e))
    eventBus.on('payment.failed', (e) => sentry.capture(e))
    // можно подписать несколько наблюдателей
  }
}
```

**Правило для сред:**
- Прод → подход Б. Модуль эмитит события. LoggerModule подписан.
- Dev → гибрид. Б как основа + минимальный console.log через env.

> Observability — это не новая концепция в DCA. Это применение event-driven слоя для наблюдения.

**Связь с error handling:** generic обработчик ошибок — это точка входа в observability для ещё не классифицированных проблем. Observability и error handling питают друг друга.

## Группа IV — Как система эволюционирует

### 09. Версионирование контрактов

**Три модели владения контрактом — от худшего к лучшему:**

**Code-first** — бэк пишет код, потом генерит схему. Контракт = побочный продукт реализации. Фронт всегда реактивный.

**Schema-first** — OpenAPI YAML написан явно, код генерируется с обеих сторон. Контракт = источник правды. Swagger → openapi-fetch.

**Contract-first + versioning** — схема в отдельном пакете, версионируется явно. Обе стороны подписаны на версию. gRPC .proto — крайний случай этого подхода.

> gRPC обрадовал потому что .proto — это единственный источник правды из которого генерируется всё: клиент, сервер, типы, валидация. API-first на максималках.

**Правило изменений:**

✓ Additive — новое поле, новый необязательный параметр, новый endpoint. Старые consumers не замечают.

✗ Breaking — переименовать поле, изменить тип, убрать endpoint. Всегда новая версия + deprecation период.

**Жизненный цикл версии (consumer-driven versioning):**

```
v1 живёт         → все consumers на v1
       ↓
additive change  → добавляешь поле, v1 не трогаешь
       ↓
breaking change  → выпускаешь v2, v1 продолжает жить
       ↓
deprecation      → объявляешь: v1 умрёт через 3 месяца
       ↓
все мигрировали  → убиваешь v1
```

**Что нужно раскрыть:**
- Как версионировать event payload — не сломав подписчиков
- Consumer-Driven Contract tests — автоматическая проверка совместимости

### 10. Границы системы

Теоретически абстракция никогда не заканчивается: IT система → мир → вселенная. Но практически границу нужно определить явно. Иначе домен не знает где он заканчивается.

**Граница — это стек слоёв, каждый из которых защищает домен от разного типа "чужого":**

- **Транспорт** (HTTP, WebSocket) — невалидный запрос, неправильный метод
- **Схема** (OpenAPI, DTO) — неправильный формат, не тот тип. Ловится валидацией.
- **Auth / AuthZ** — правильный запрос, но нет прав. Контракт доступа.
- **Domain** — данные валидны, но нарушают бизнес-правила. Domain violation.

> Граница — это не одна линия. Это стек слоёв, каждый из которых защищает домен от разного типа "чужого".

**Адаптер = Anti-Corruption Layer.** Чужая модель не проходит дальше адаптера:

```typescript
// БЕЗ адаптера — чужая модель внутри домена
orderService.create({
  stripeCustomerId: 'cus_xxx',   // это Stripe, не домен
  stripePaymentMethod: 'pm_xxx'  // это тоже Stripe
})

// С адаптером — домен говорит на своём языке
class StripeAdapter implements PaymentPort {
  pay(orderId: string, amount: number) {
    return stripe.charge({ customer: this.toStripeId(orderId), amount })
  }
}
orderService.create({ orderId, amount })
// домен не знает про Stripe вообще
```

**Model bleeding — главный антипаттерн границы.** Чужая модель просочилась через границу внутрь домена. Технически работает. Тесты зелёные. Но домен начинает зависеть от деталей внешнего мира. Обнаруживается когда сторонний сервис меняет API — и ломается половина домена.

**Симптомы:** названия из чужого API в твоих моделях. DTO стороннего сервиса передаётся напрямую в бизнес-логику.

**Лечение:** адаптер на каждый внешний сервис. Маппинг на границе. Домен оперирует только своими моделями.

**OpenAPI — контракт на границе фронт/бэк. Но кто им владеет?**

- Бэк диктует — фронт подстраивается. Классика, но фронт всегда реактивный.
- Контракт первичен — оба генерируют код из схемы. Никто не диктует, схема — источник правды. Это DCA-подход.

> В DCA контракт на границе — это не артефакт бэкенда. Это отдельный модуль которым владеет команда, не сторона.

**Что нужно раскрыть:**
- Как граница меняется при росте: монолит → модули → микросервисы
- Кто владеет OpenAPI контрактом — процесс и инструменты contract-first разработки

## Группа V — Тестирование

### 11. Тестирование

**Correctness by construction.** Правильная структура делает неправильное состояние невозможным или сразу видимым:

- TypeScript — правильная композиция типов → компилятор ловит ошибки → часть тестов не нужна вообще.
- DCA — правильная композиция контрактов + конфигов → flow описывает все маршруты → тесты вытекают автоматически.

> Если архитектура правильная — тесты это просто обход уже описанных маршрутов. Непокрытый маршрут = дыра в конфиге, видна сразу.

**Три уровня тестирования вытекают из архитектуры:**

**Контракт модуля → unit тест.** Интерфейс декларирует вход и выход. Тест просто проверяет что контракт выполнен. Для Pure модулей тривиально.

**Flow / State Machine → integration тест.** Все переходы уже описаны в конфиге. Тест-кейсы = маршруты по состояниям:

```javascript
const checkoutFlow = {
  states: {
    idle:       { on: { SUBMIT: 'validating' } },
    validating: { on: { VALID: 'submitting', INVALID: 'failed' } },
    submitting: { on: { SUCCESS: 'done', NETWORK_ERROR: 'retrying' } },
    retrying:   { on: { SUCCESS: 'done', EXHAUSTED: 'failed_permanent' } },
  }
}

// маршруты для тестов вытекают сами:
// ✓ idle → validating → submitting → done          (happy path)
// ✓ idle → validating → failed                     (validation error)
// ✓ idle → validating → submitting → retrying → done
// ✓ idle → validating → submitting → retrying → failed_permanent
```

**User Story → Flow → e2e тест (Playwright).** Один и тот же конфиг описывает и поведение системы и сценарий теста. Источник правды один для продакта, разработчика и QA.

**Каждый тип модуля тестируется по-своему:**

- Pure — нет зависимостей, нет моков. Дал вход → проверил выход.
- Stateful — тестируем контракт доступа и нотификации. Изменил состояние → подписчики получили событие.
- Effectful — через мок порта. Реальный HTTP не нужен:

```typescript
const mockPaymentPort: PaymentPort = {
  pay: jest.fn().mockResolvedValue({ success: true })
}
const orderService = new OrderService(mockPaymentPort)
await orderService.checkout(cart)
```

**Тесты тоже декларативны.** Если система строится через конфиги — тесты тоже можно описывать декларативно. Конфиг описывает маршрут, фреймворк его обходит.

## Философский слой

*Это не отдельный принцип архитектуры — это метафора поверх всего.*

Это не философия придуманная в вакууме. Это паттерны увиденные в коде — и оказалось что они работают везде. Проектирование системы и проектирование жизни — одно и то же по структуре.

> Хорошая система не требует героизма. Она спроектирована так, что правильное поведение — это путь наименьшего сопротивления. В коде и в жизни.

### Перевод понятий: Архитектура → Жизнь

- **Модуль** — человек, проект, привычка, навык. Единица с зоной ответственности.
- **Контракт** — ожидания, договорённости, обязательства перед собой и другими.
- **События** — обстоятельства, случайности, внешние воздействия. Ты не контролируешь все события.
- **Effectful модули** — силы вне твоего контроля. Можно адаптироваться, нельзя контролировать.
- **Декларация** — цели, принципы, рамки. "Что хочу" без жёсткого "как именно".
- **Flow** — навыки адаптации. Как реагируешь на события — твой внутренний конечный автомат.
- **Unknown состояние** — "не знаю что происходит". Нормальное состояние, не паника. Требует проверки, не героизма.

### Слабая связанность

Event-driven в жизни: ты реагируешь на события, но не управляешь всем. Люди не должны быть "жёстко зависимы" друг от друга — это разрушает систему при первом же сбое.

> Слабая связанность в отношениях — это не равнодушие. Это устойчивость.

### LEGO метафора

Привычки, проекты, отношения — это модули. Добавляешь новый (хобби, навык) — система растёт. Убираешь токсичный — ничего не ломается, если изоляция была правильной.

### Три типа жизненных ошибок

**Expected** — риски которые заложил. Есть план Б. Не больно.

**Unexpected** — форс-мажоры. Попадают в "generic обработчик" — рефлексию. Потом становятся опытом и переходят в Expected.

**Domain violation** — нарушение собственных принципов. Самый болезненный тип — ты знал правило.

> Мудрость — это библиотека классифицированных исключений. Опыт превращает Unexpected в Expected.

### Observability = рефлексия

Дневник, ретроспектива, обратная связь — это observability себя. Без рефлексии нет итерации.

- Реактивно: что-то пошло не так → начинаешь анализировать. Рефлексия как пожарный инструмент.
- Проактивно: регулярная ретроспектива. Проблемы видны до того как стало больно.

### Версионирование договорённостей

Когда меняешь "правила игры" — в команде, в отношениях, в проекте — либо делаешь это явно, либо люди продолжают жить по старому контракту и получают сюрприз.

Молчаливое изменение ожиданий — это breaking change без новой версии. Система ломается, но никто не понимает почему.

> Explicit deprecation лучше чем молчаливое несоответствие — и в коде, и в жизни.

### Цикл эволюции — одинаков в системе и в жизни

```
Observability (рефлексия) → Ошибки (опыт) → Контракты (принципы) → Версия (рост)
```

### Философские корни

DCA ближе всего к трём течениям одновременно:

**Стоицизм** — работа с ошибками и контролем. Pure модули = твоя зона контроля. Effectful = внешний мир, принимаешь как есть. Ошибки не враги — переходы. "Stoic Development" — существующий термин для этого пересечения.

**Даосизм** — wu wei, путь наименьшего сопротивления. "Хорошая система не требует героизма" — это почти дословный Дао. Архитектура которая работает сама по себе без борьбы.

**Systems Thinking** — мир организован как взаимосвязанное целое. Паттерны повторяются на всех уровнях. Видишь взаимосвязи, а не вещи. Это прямо про DCA.

Стоики дали работу с ошибками и контролем. Дао — идею что правильная структура работает без сопротивления. Systems Thinking — идею что всё связано и паттерны повторяются на всех уровнях.

### Дальнейшее исследование

Это направление можно развивать глубже. Есть ещё несколько философских течений которые потенциально резонируют с DCA:

- **Teleology (Аристотель)** — каждый модуль имеет цель, не просто функцию. Усиливает определение зоны ответственности.
- **Phenomenology** — контракт это то как модуль воспринимается снаружи, не то что внутри. Буквально про разделение интерфейса и реализации.
- **Constructivism** — система строит себя через опыт. Наш цикл observability → ошибки → контракты → версия это и есть constructivism.
- **Pragmatism** — истина это то что работает. DCA не академическая чистота, а практическая применимость — это прагматизм в действии.

*Пока это просто заметки для дальнейшего размышления. Связь между этими течениями и конкретными принципами DCA требует отдельного разговора.*
