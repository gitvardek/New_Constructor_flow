# Agent Layer

`Agent Layer` не является частью ядра DCA. Это прикладной слой исполнения, через который изменения в системе могут выполнять люди, CI-процессы, кодогенераторы и AI-агенты.

Текущая договорённость для этого репозитория:
- `DCA` документы в `_architecture/` считаются более ценным источником истины
- `.claude/*` пока рассматривается как legacy operational слой под Claude
- при конфликте между DCA документами и старыми Claude-инструкциями приоритет у DCA

## Зачем нужен Agent Layer

DCA описывает:
- модули
- контракты
- события
- декларации
- flow

Но сама по себе архитектура не отвечает на вопрос, **кто именно реализует изменение** и **по каким правилам это изменение вносится**.

Именно это закрывает `Agent Layer`.

## Основной принцип

Архитектура первична, агент вторичен.

Это означает:
- система не должна зависеть от конкретного AI-инструмента
- агент не определяет архитектуру
- агент работает внутри уже заданных контрактов, ограничений и flow
- чем лучше формализована система, тем безопаснее делегировать её изменение агенту

## Что входит в Agent Layer

- роли исполнителей: `planner`, `tester`, `code-reviewer`, `module-builder`
- правила постановки задач
- шаблоны промптов и инструкций
- критерии приёмки результата
- правила валидации изменений
- ограничения на область ответственности агента

## Что не входит в Agent Layer

- доменная архитектура системы
- runtime-контракты модулей
- бизнес-логика приложения
- модель данных как таковая

Это остаётся в `Core` и в декларативных слоях системы.

## Как Agent Layer связан с DCA

DCA делает систему агент-дружественной за счёт явности:
- модуль имеет границы
- контракт формализован
- flow описан
- архитектурные решения зафиксированы

За счёт этого агент может:
- читать систему
- понимать допустимые точки изменения
- генерировать код в известных границах
- валидировать результат против контрактов и правил

Иными словами:

> Declarative Contract Architecture позволяет не только проектировать системы, но и делегировать их реализацию агентам через формализованные контракты и декларации.

## Типы исполнителей

В рамках этого репозитория полезно различать несколько типов исполнителей:

- человек
- AI-агент
- кодогенератор
- CI/CD automation

Все они являются не частью доменной модели, а частью слоя исполнения изменений.

## AI-агент как исполнитель

AI-агент в этой модели лучше понимать не как “модуль приложения”, а как `change-time executor`:

- он не участвует в runtime системы
- он не является частью бизнес-потока приложения
- он изменяет код, конфиги, контракты и документацию
- он работает по входному task-контракту

Поэтому для AI-агента особенно важны:
- чёткие входы
- ограничение write scope
- expected output
- acceptance criteria
- явные запреты

## Task Contract для агента

Промпт не должен считаться полноценным контрактом сам по себе.

Полезнее рассматривать задачу агента как `Task Contract`, который включает:
- цель
- контекст
- затрагиваемые файлы
- файлы, которые нельзя менять
- ограничения
- ожидаемый результат
- способ проверки

Промпт в этом случае выступает транспортом этого контракта, а не заменой контракта.

## Практический вывод для репозитория

Текущие файлы в `.claude/` относятся именно к `Agent Layer`:
- роли агентов
- правила их поведения
- ограничения
- ожидания к результату

Это не ядро мета-фреймворка и не сама архитектура DCA.
Это operational слой, через который архитектура может быть реализована и сопровождаться.

## Mapping на vendor-neutral workflow

Legacy роли не являются canonical процессной моделью для всех сред.
Для vendor-neutral workflow используется следующая нормализация:

- `planner` → `Plan`
- `module-builder` → `Implement`
- `tester` → `Verify`
- `code-reviewer` → `Review`

Это означает:
- в `.claude/*` роли могут оставаться как operational интерфейс Claude
- в Codex и в общих документах primary model — это фазы workflow, а не vendor-specific имена агентов

## Направление развития

Если эта часть будет расти, её можно развивать в отдельную подсистему:
- vendor-neutral task contracts
- mapping под разные агентные среды
- правила для Claude / Codex / других инструментов
- единые acceptance criteria для всех исполнителей

Пока этот слой логично держать в `_docs/`, а не в `_architecture/`, потому что он описывает не саму архитектуру системы, а способ её исполнения.
