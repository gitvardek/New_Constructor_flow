# Workflow V1

Минимальный рабочий workflow для этого репозитория.

Это не “идеальная теория процесса”, а operational схема, по которой можно реально вести задачи без постоянного смешения архитектуры, bootstrap-работ и feature-реализации.

---

## 1. Тип задачи

Перед началом любая задача должна быть отнесена к одному из двух типов:

### `bootstrap task`

Задача считается bootstrap-задачей, если она поднимает или чинит один из базовых контуров:

- codegen path
- package wiring
- test path
- build path
- runtime path

Примеры:
- настроить `pnpm generate:api`
- завести `openapi-fetch`
- подключить workspace imports
- поднять запускаемый baseline для Next или Nest

### `feature task`

Задача считается feature-задачей, если она реализует конкретный модуль, endpoint, UI flow или вертикальный slice поверх уже готовых контуров.

Примеры:
- `health`
- `settings`
- `session`
- `notifications`

### Правило переключения

Если в ходе feature-задачи выясняется, что базовый контур не готов, задача должна быть разделена:

1. сначала bootstrap-задача
2. потом возврат к feature-задаче

Нельзя silently чинить половину toolchain внутри feature-задачи и продолжать делать вид, что это обычная feature.

---

## 2. Baseline по умолчанию

Для этого репозитория baseline качество подразумевается всегда.

Это означает:
- не существует отдельного нормального режима `canonical`
- не существует отдельного нормального режима `spike`
- задача должна по умолчанию соответствовать source of truth, package boundaries и baseline stack

### Temporary Deviation

Если baseline временно недостижим, это не становится отдельным режимом задачи.
Это считается явным исключением.

Такое исключение должно быть проговорено отдельно:
- что именно недоступно
- почему без этого нельзя закончить задачу полностью
- какой scope у временного отклонения
- что потом нужно убрать

Temporary deviation не является нормой и не должен silently оставаться в коде.

---

## 3. Readiness Gate

Перед фазой `Implement` нужно пройти readiness gate.

Проверить:

1. Есть ли source of truth?
2. Есть ли codegen path?
3. Есть ли package boundary?
4. Есть ли test path?
5. Есть ли build/runtime path?

### Интерпретация

Если отсутствуют два и более пункта:
- это не feature-ready задача
- её нужно считать bootstrap-задачей

Если отсутствует один пункт:
- можно продолжать, но этот риск должен быть явно озвучен

---

## 4. Фазы работы

Работа идёт по фазам:

1. `Plan`
2. `Implement`
3. `Verify`
4. `Review`

---

## 5. Phase: Plan

На этапе `Plan` нужно определить:

- тип задачи: `bootstrap` или `feature`
- source of truth
- scope изменений
- verification strategy
- есть ли temporary deviation или нет

Перед планированием нужно проверить:
- релевантные архитектурные документы
- `packages/contracts/*`, если задача затрагивает transport contract
- `_docs/decisions.md`
- существующие тесты и принятые паттерны в коде

### Preflight для новой доменной сущности

Если задача вводит новую доменную сущность или новый крупный модуль, перед формулировкой плана нужно отдельно восстановить локальную истину репозитория.

Минимальный порядок:
1. `CODEX.md`
2. `_docs/decisions.md`
3. релевантные файлы из `_architecture/*`
4. релевантные контракты из `packages/contracts/*`
5. существующую реализацию, планы и шаблоны, если они уже есть

После такого preflight исполнитель должен:
- перечислить уже принятые решения, влияющие на сущность
- отделить их от новых предложений
- не задавать вопросы, если ответ уже есть в документах, контрактах или коде
- задавать только вопросы о реальных пробелах или конфликтах между источниками

### Результат планирования

Минимально должно быть ясно:
- что именно делаем
- почему это именно этот тип задачи
- можно ли сделать baseline implementation без отклонений
- если нет, какое именно отклонение требуется

Если задача нетривиальная, результат `Plan` нужно сохранять в `_plans/{task-name}.md`.

Минимальная структура такого плана:
- описание задачи
- task type
- goal
- scope
- non-goals
- constraints
- затрагиваемые файлы
- файлы, которые нельзя трогать
- пошаговый план
- риски и breaking changes
- verification

---

## 6. Phase: Implement

В этой фазе код по умолчанию должен соответствовать baseline.

Обязательны:
- source-of-truth alignment
- package boundaries
- codegen alignment
- соответствие baseline stack и архитектуре

Если заранее согласовано temporary deviation, оно должно быть:
- минимальным
- локализованным
- явно отмеченным
- не маскируемым под finished baseline implementation

---

## 7. Phase: Verify

Проверка должна соответствовать типу задачи и наличию или отсутствию temporary deviation.

Что проверяется:

- тесты
- build
- codegen
- package boundaries
- runtime path, если это заявлено в expected result

По умолчанию проверка должна подтвердить:
- работоспособность контура
- отсутствие неоговорённых временных обходов
- соответствие baseline

После code changes по умолчанию нужно:
- дописать недостающие тесты
- запустить `pnpm test`
- явно сказать, если полный suite не удалось прогнать в текущей среде

Если есть temporary deviation, проверка должна дополнительно подтвердить:
- отклонение явно ограничено заявленным scope
- отклонение не замаскировано под finished implementation
- зафиксировано, что именно нужно убрать позже

---

## 8. Phase: Review

Review делается относительно baseline по умолчанию.

То есть:
- review обязан ругать все неоговорённые временные обходы и несоответствия baseline
- если был явно согласован temporary deviation, review проверяет, что он действительно локализован и честно обозначен

### Формат review

- findings first
- затем assumptions / open questions
- затем короткий summary

### Что обязательно проверять в review

- регрессии и удалённые тесты
- auth без обходов
- контракты и отсутствие ручного дублирования типов
- слои и package boundaries
- API вызовы только через `packages/api-client`
- фильтрацию, сортировку, soft delete и audit, если они затронуты
- безопасность и утечки секретов
- достаточность тестов

---

## 9. Definition of Done

### Для `bootstrap task`

Задача завершена, когда:
- контур поднят
- его можно использовать в следующих задачах
- проверка этого контура выполнена

### Для `feature task`

Задача завершена, когда:
- feature реализована
- использует уже готовые контуры
- source of truth соблюдён
- codegen path работает
- package boundaries соблюдены
- tests/build/runtime проходят в рамках заявленного результата
- временных обходов не осталось, кроме явно согласованного temporary deviation

---

## 10. Формат постановки задачи

Желательно, чтобы задача явно содержала:

- `Task type`: `bootstrap` / `feature`
- `Goal`
- `Scope`
- `Verification`
- при необходимости: `Temporary Deviation`

Если это не указано пользователем, исполнитель обязан определить это сам и проговорить перед реализацией.

---

## 11. Простое правило workflow

Нельзя начинать `feature task`, пока для неё не готов bootstrap.

Это базовое правило, которое должно предотвращать ситуацию, когда команда сначала пишет “правильный” код, а потом оказывается, что половина инфраструктуры для него ещё не существует.
