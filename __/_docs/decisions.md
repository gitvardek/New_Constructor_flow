# Decision Log

История архитектурных решений проекта.
Обновляется агентом после каждого значимого решения.

Формат каждой записи:
- **Дата** — когда принято решение
- **Контекст** — что происходило, какая была проблема
- **Решение** — что выбрали
- **Альтернативы** — что рассматривали
- **Причина** — почему выбрали именно это
- **Последствия** — что это значит для кодовой базы

## [2026-03] NestJS on Fastify вместо Express

**Контекст:** Выбор HTTP адаптера для NestJS.

**Решение:** Fastify.

**Альтернативы:** Express (дефолт NestJS).

**Причина:** Fastify даёт ~30% прирост производительности, встроенная схема валидации, лучшая типизация из коробки. Express выбирают для совместимости с legacy middleware — у нас такого нет.

**Последствия:** Некоторые Express-специфичные middleware несовместимы. При добавлении новых пакетов проверять поддержку Fastify.

## [2026-03] Keycloak для авторизации

**Контекст:** Нужна авторизация с ролями и возможностью SSO.

**Решение:** Keycloak OIDC.

**Альтернативы:** Auth0, собственный JWT, Supertokens.

**Причина:** Self-hosted (нет зависимости от внешнего сервиса), поддержка SSO и федерации, гибкая система ролей через realm/resource roles, open source.

**Последствия:** NEVER реализовывать собственную auth логику. Все роли и claims — только из Keycloak токена.

## [2026-03] Soft delete как дефолт для всех сущностей

**Контекст:** Нужна стратегия удаления данных.

**Решение:** Soft delete через `deletedAt` поле в `FullAuditFields`.

**Альтернативы:** Hard delete, archive таблицы.

**Причина:** Возможность восстановления данных, audit trail, безопасность от случайного удаления. Физическое удаление — фоновый cron по расписанию.

**Последствия:** Все Repository по умолчанию фильтруют `WHERE deletedAt IS NULL`. Для получения удалённых записей — передавать `withDeleted=true`.

## [2026-03] SSE вместо WebSocket для уведомлений

**Контекст:** Нужна доставка уведомлений в реальном времени.

**Решение:** SSE (Server-Sent Events).

**Альтернативы:** WebSocket, polling.

**Причина:** Уведомления однонаправленные (сервер → клиент). SSE работает через обычный HTTP, автореконнект из коробки, проще в реализации. WebSocket нужен только для двусторонней коммуникации (чат, совместное редактирование).

**Последствия:** При нескольких инстансах бэкенда — нужен Redis Pub/Sub для синхронизации SSE соединений между инстансами.

## [2026-03] openapi-fetch для API клиента

**Контекст:** Нужен типизированный HTTP клиент на фронте.

**Решение:** openapi-fetch с генерацией типов из OpenAPI spec.

**Альтернативы:** axios, fetch напрямую, tRPC, react-query с ручными типами.

**Последствия:** Изменение контракта → `pnpm generate:api` → типы обновляются автоматически. Все API вызовы — только через сгенерированный клиент.

## [2026-03] Два источника переводов (i18n)

**Контекст:** Нужна локализация интерфейса и пользовательского контента.

**Решение:** Статика (JSON файлы) для UI строк + динамика (API + БД) для контента.

**Альтернативы:** Только статика, только динамика.

**Причина:** UI строки (кнопки, лейблы) меняются только с деплоем — JSON оптимален. Пользовательский контент (названия товаров, статьи) должен меняться без деплоя через админку.

**Последствия:** NEVER дублировать ключи между источниками. UI строка → всегда JSON. Контент → всегда API.

## [2026-03] Стратегии хранения файлов (local / s3 / minio)

**Контекст:** Нужна загрузка файлов, разные проекты имеют разную инфраструктуру.

**Решение:** Единый контракт, три провайдера через `FileUploadModule.forRoot({ strategy })`.

**Альтернативы:** Только S3, только локальное хранилище.

**Причина:** Маленькие проекты не нуждаются в S3. Большие проекты не могут хранить файлы на сервере. Единый интерфейс позволяет менять провайдер без изменения кода модулей.

**Последствия:** Фронт всегда получает `url` — не знает откуда файл. Физическое удаление файлов — только через фоновый cron после soft delete.

## [2026-03] AuditActor заполняется через AuditContext сервис

**Контекст:** `AuditActor` (createdBy/updatedBy) — снимок пользователя на момент действия. Repository не должен знать о HTTP контексте — это нарушает слои.

**Решение:** `AuditContext` — отдельный request-scoped сервис.

```typescript
// Инжектируется в Repository через DI, не через HTTP
@Injectable({ scope: Scope.REQUEST })
export class AuditContext {
  private actor: AuditActor

  setActor(user: SessionUser) {
    this.actor = {
      id: user.id,
      displayName: user.displayName,
      firstName: user.firstName,
      lastName: user.lastName,
      email: user.email,
    }
  }

  getActor(): AuditActor {
    return this.actor
  }
}

// KeycloakGuard устанавливает актора после верификации токена
// Repository читает актора через AuditContext
```

**Альтернативы:** Передавать актора явным параметром в каждый метод Repository (verbose), использовать AsyncLocalStorage (сложнее).

**Причина:** Request-scoped DI — стандартный NestJS паттерн. Чисто, без нарушения слоёв.

**Последствия:** Repository не принимает актора параметром. AuditContext автоматически инжектируется. KeycloakGuard обязан вызывать `auditContext.setActor()`.

## [2026-03] filter[field][between] — формат и поведение при невалидных данных

**Контекст:** `between` в filter.yaml принимает строку `"18,65"`. Парсинг строки в два значения потенциально хрупкий.

**Решение:** Оставить строковый формат, но строго зафиксировать поведение.

**Правила парсинга:**
- Формат строго: `"value1,value2"` — ровно два значения через запятую
- Пробелы вокруг запятой игнорируются: `"18, 65"` → `[18, 65]`
- Меньше или больше двух значений → `400 VALIDATION_ERROR`
- Для дат — ISO 8601 формат обязателен

**Альтернативы:** Два отдельных параметра `filter[age][gte]=18&filter[age][lte]=65` — многословно но явно. Оставлено как дополнительная опция.

**Причина:** `between` удобнее для диапазонов дат в UI. Два параметра используются когда нужен только один конец диапазона.

**Последствия:** `FilterQueryPipe` строго валидирует формат `between`. При невалидном значении — всегда `400 VALIDATION_ERROR` с деталями.

## [2026-03] Дефолтная локаль вынесена из контракта в конфиг

**Контекст:** `LocalizedString` в i18n.yaml требует поле `ru` как обязательное — это хардкодит русский как дефолтную локаль прямо в OpenAPI схеме.

**Решение:** Считать `ru` дефолтной локалью фреймворка с возможностью переопределения.

**Правило:** В `LocalizedString` обязательным остаётся `ru` — это дефолт для наших проектов. Если проект меняет дефолтную локаль — он переопределяет `LocalizedString` в своём контракте через `allOf`:

```yaml
# В проекте где дефолт = en
LocalizedString:
  allOf:
    - $ref: '../../meta-framework/contracts/common/i18n.yaml#/components/schemas/LocalizedString'
  required: [en]  # переопределяем обязательное поле
```

**Альтернативы:** Сделать все поля опциональными и проверять дефолт на бэкенде — теряем типизацию на фронте.

**Причина:** Большинство наших проектов русскоязычные. Явный `required: [ru]` даёт ошибку компиляции TypeScript если перевод не заполнен — это ценно.

**Последствия:** Проекты с другой дефолтной локалью должны явно переопределить `LocalizedString`. Это осознанное решение, не забыть документировать в README проекта.

## [2026-03] SessionUser отделён от User

**Контекст:** `AuthSession.user` ссылался на полную `User` схему которая включает `FullAuditFields` (createdBy, deletedAt и т.д.). Сессия не должна возвращать audit данные.

**Принцип:** `User` = полная модель для admin/управления. `SessionUser` = минимальный набор для работы приложения. `UserProfile` = публичные данные для других пользователей.

**Последствия:** Три разные схемы для одной сущности — это нормально. Каждая служит своей цели. NEVER использовать `User` там где достаточно `SessionUser`.

## [2026-03] Bulk операции через BulkSelection с confirmCount

**Контекст:** Нужен стандарт для массовых операций. Главный риск — случайное удаление/изменение большого количества записей.

**Решение:** `BulkSelection` с двумя режимами и `confirmCount` как защитный механизм.

**Принцип confirmCount:** Клиент сначала видит сколько записей будет затронуто (из meta.total), потом передаёт это число в запросе. Если за время между запросами количество изменилось — бэкенд отклоняет операцию с `409 BULK_COUNT_MISMATCH`. Это защищает от race condition.

**Альтернативы:** Транзакции с preview (сложнее), только по ID (не масштабируется).

**Последствия:** Фронт всегда показывает пользователю сколько записей будет затронуто до выполнения операции. UX паттерн: "Удалить 247 пользователей?" → подтверждение → запрос с confirmCount: 247.

## [future] Экспорт данных — отложено до реализации зависимостей

**Контекст:** ExportModule был описан в контрактах как generic модуль, но оказался единственным который не может работать изолированно.

**Решение:** Убран из generic контрактов фреймворка.

**Причина:** ExportModule требует одновременно Redis + BullMQ + FileUploadModule + NotificationModule. Держать его в common/ наравне с pagination.yaml вводило в заблуждение — это не самодостаточный кирпич.

Для простых случаев (CSV, небольшие таблицы) достаточно синхронного стрима — никакого job в БД не нужно.

**Когда реализовывать:** После того как в проекте уже работают Redis, FileUploadModule, NotificationModule.

**Паттерн реализации:**
```
GET /resource/export?format=xlsx&filter[...]
  → создать ExportJob в БД (status: pending)
  → поставить в BullMQ очередь
  → вернуть { id, status: "pending" }

Worker:
  → выполнить запрос с фильтрами
  → сгенерировать файл (csv/xlsx/pdf)
  → загрузить через FileUploadModule
  → обновить job (status: done, downloadUrl)
  → уведомить через NotificationModule (SSE)

GET /resource/export/:jobId → ExportJob (polling)
GET /resource/export/:jobId/download → 302 redirect
```

**Форматы:** CSV (нативно), XLSX (exceljs), PDF (puppeteer/pdfkit — тяжёлые зависимости).
**Контракт:** описывать в конкретном проекте под его форматы и поля.

## [2026-03] Setting не использует AuditFields

**Контекст:** `Setting` через `allOf` подключал `AuditFields` — `createdAt`, `updatedAt`, `createdBy`, `updatedBy`.

**Решение:** Простая схема только с `updatedAt`.

**Причина:** История "кто поставил тёмную тему и когда создал настройку" не нужна ни в одном реальном проекте. `AuditFields` — overhead. `updatedAt` достаточен для кеш-инвалидации на фронте.

**Последствия:** `Setting` не имеет `id` — ключом является `key` + `userId`. Это упрощает БД схему (нет отдельного UUID для каждой настройки).

## [2026-03] BulkSelection через oneOf с additionalProperties: false

**Контекст:** Исходный `BulkSelection` не имел `required` — пустой объект проходил schema validation.

**Решение:** `oneOf` с двумя явными вариантами, каждый с `required` и `additionalProperties: false`.

**Причина:** `additionalProperties: false` + `oneOf` — единственный способ сделать взаимоисключающие поля строгими на уровне OpenAPI схемы. Без этого любой невалидный запрос проходил бы через schema validation.

**Последствия:** Нельзя передать `ids` и `selectAll` одновременно — это ошибка на уровне схемы, не бизнес-логики.

## [2026-03] Translation без AuditFields и без isApproved

**Контекст:** `Translation` использовал `AuditFields` (createdAt, updatedAt, createdBy, updatedBy) и имел поле `isApproved` для approval workflow переводчика.

**Решение:** Простая схема только с `updatedAt`. `isApproved` убран полностью.

**Причина для AuditFields:** По той же логике что `Setting` — история "кто добавил перевод" не нужна в generic фреймворке. `updatedAt` достаточен для кеш-инвалидации.

**Причина для isApproved:** Approval workflow (переводчик одобряет перевод) — фича для крупных команд с отдельной ролью translator. В большинстве проектов переводы вносит разработчик напрямую. Для generic фреймворка это overengineering.

**Последствия:** Если проекту нужен approval workflow — расширять `Translation` схему локально, добавляя `isApproved` и роль `translator` в Keycloak. `TranslationCoverage.byLocale` упрощён — убрано поле `approved`.

## [2026-03] AuditActor — displayName как обязательное вычисляемое поле

**Контекст:** `AuditActor` имел `required: [id]` — имя и email опциональны. Фронт получал актора без имени и вынужден был писать fallback логику в каждом месте.

**Решение:** `required: [id, email, displayName]`. Добавлено вычисляемое поле `displayName`.

**Логика вычисления (в KeycloakGuard / AuditContext):**
```typescript
displayName = [firstName, lastName].filter(Boolean).join(' ') || email
```

**Причина:** `email` всегда есть в Keycloak (это логин). `displayName` вычисляется один раз на бэкенде — фронт не пишет fallback в каждом компоненте.

**Последствия:** `SessionUser` тоже получил `displayName` в `required` — KeycloakGuard вычисляет его при верификации токена. `AuditContext` копирует `displayName` из `SessionUser` напрямую.
