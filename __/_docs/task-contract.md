# Task Contract

`Task Contract` — это формат задачи для Codex.

Промпт не считается полным контрактом сам по себе. Полезнее описывать задачу как набор обязательных полей.

## Минимальный формат

В идеале задача должна содержать:
- `Goal` — что нужно получить
- `Scope` — какие файлы или области можно менять
- `Non-goals` — что менять нельзя
- `Constraints` — архитектурные и технологические ограничения
- `Expected Result` — какой итог считается успешным
- `Verification` — как проверить результат

## Пример короткой задачи

```md
Goal:
Привести frontend baseline к Next.js в документах и каркасе.

Scope:
- _docs/*
- _architecture/*
- apps/web/*

Non-goals:
- не трогать backend реализацию
- не добавлять реальные зависимости

Constraints:
- DCA документы выше legacy Claude-файлов
- validation baseline = Zod

Expected Result:
- документы согласованы
- apps/web отражает Next-oriented структуру

Verification:
- проверить поиском старые маркеры
- показать итоговую структуру
```

## Если пользователь не дал полный контракт

Тогда Codex должен восстановить его из контекста:
- взять `Goal` из запроса пользователя
- вывести `Constraints` из `CODEX.md`, `packages/contracts/*`, `_architecture/*`, `_docs/decisions.md`, `_docs/coding-rules.md`
- предположить разумный `Scope`
- явно сообщить о сделанных допущениях

## Правила хорошего Task Contract

- цель должна быть проверяемой
- scope должен ограничивать область записи
- ограничения должны быть конкретными
- expected result должен быть наблюдаемым
- verification должен быть реалистичным для текущей среды

## Типы задач

### Локальное изменение

Для маленькой задачи достаточно:
- `Goal`
- `Scope`
- `Verification`

### Структурное изменение

Для изменений структуры, архитектуры или контрактов нужны все поля.

### Review task

Для review-задач контракт выглядит так:
- `Goal`: найти проблемы
- `Scope`: конкретный diff, файлы или область
- `Constraints`: findings-first, без переписывания кода
- `Expected Result`: список проблем по приоритету
- `Verification`: ссылки на файлы и аргументация

Для нетривиальной implement-задачи желательно также указать:
- где должен быть сохранён план в `_plans/`
- нужно ли обновлять `_docs/decisions.md`, если появится новое архитектурное решение

## Что Codex должен делать с Task Contract

Перед выполнением Codex должен:
1. определить, полный контракт или нет
2. восстановить недостающие поля из репозитория
3. выбрать режим: `Plan`, `Implement`, `Verify`, `Review`
4. работать в пределах этих ограничений

Для нетривиальных задач Codex должен отдельно определить:
5. `Task type`: `bootstrap` или `feature`
6. есть ли `Temporary Deviation` от baseline или нет

Если пользователь не указал эти поля, Codex обязан явно назвать выбранные значения перед реализацией.

## Baseline по умолчанию

Для этого репозитория baseline качество подразумевается по умолчанию.

Это означает:
- отдельный режим `canonical` не нужен
- любая задача должна соответствовать architecture, contracts и coding rules
- временное упрощение не считается отдельным нормальным mode

Если baseline временно недостижим, это должно быть оформлено как явное отклонение:
- `Temporary Deviation`
- причина
- scope отклонения
- что именно нужно потом убрать

Такое отклонение считается exception path, а не альтернативным стандартным режимом.

## Связь с Agent Layer

`Task Contract` — это vendor-neutral форма задачи.

Legacy роли:
- `planner`
- `tester`
- `code-reviewer`
- `module-builder`

являются частными operational представлениями этого контракта, но не заменяют его.
